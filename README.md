# החצר של יודה - POC מערכת CRM

מערכת CRM ראשונית (Proof of Concept) עם שני מודולים: **ניהול חברים** ו**ניהול סדנאות ואירועים**, והחיבור הדו-כיווני ביניהם (הרשמות ונוכחות).
רצה מקומית בלבד, בדפדפן, עם בסיס נתונים SQLite בקובץ מקומי. ללא שרת חיצוני, ענן או מפתחות API.

## טכנולוגיות

React + TypeScript + Vite + Tailwind CSS (Frontend) | Node.js + Express + TypeScript (Backend, REST) | SQLite + Prisma 6 | Radix UI, Lucide, גופן Heebo.

## דרישות

Node.js 20 ומעלה (נבדק על Node 24) ו-npm.

## התקנה והפעלה ב-PowerShell

התקנה ראשונית (פעם אחת): התקנת חבילות, יצירת בסיס הנתונים והטענת נתוני הדגמה.

```powershell
cd C:\Users\haim\Projects\new_crm
npm run setup
```

הפעלה יומיומית, פקודה אחת שמריצה שרת ולקוח יחד:

```powershell
npm run dev
```

פתחו בדפדפן: **http://localhost:5173**

הרצה כאפליקציה אחת (בנייה והגשה משרת יחיד) בכתובת **http://localhost:3001**:

```powershell
npm start
```

## פקודות נוספות

| פקודה | תיאור |
|---|---|
| `npm run db:migrate` | החלת מיגרציות על בסיס הנתונים (יוצר אותו אם אינו קיים) |
| `npm run db:seed` | הטענת נתוני הדגמה. בטוח להרצה חוזרת: לא יוצר כפילויות ולא מוחק או דורס נתונים שהוזנו |
| `npm run db:reset` | **איפוס מלא**: מוחק את כל הנתונים, מחיל מיגרציות ומטעין נתוני הדגמה מחדש |
| `npm test` | בדיקות אוטומטיות לתרחישים העסקיים (על בסיס נתונים נפרד `test.db`) |
| `npm run typecheck` | בדיקת TypeScript בשרת ובלקוח |
| `npm run build` | בניית שרת ולקוח |

## היכן נשמרים הנתונים

קובץ בסיס הנתונים: `server\prisma\crm.db`. הנתונים נשמרים גם לאחר סגירת המערכת.
לגיבוי מספיק להעתיק את הקובץ כשהשרת כבוי. מחיקת הקובץ ואז `npm run db:migrate` ו-`npm run db:seed` יוצרים מערכת נקייה.

## מה כלול ב-POC

- **חברים**: טבלה עם חיפוש, סינון, מיון ועימוד; הוספה ועריכה; כרטיס חבר עם טאבים. פעילים: פרטים אישיים, פעילות קבוצתית, העדפות, הגבלות, חריגות. טאבים עתידיים מוצגים כהודעה בלבד.
- **סדנאות ואירועים**: טבלה, יצירה (כולל מרובת מפגשים), סטטוסים, פרסום מדומה, הגדרות הרשמה (מגדר, גיל, ביטוח לאומי), שאלות הרשמה, נרשמים, מפגשים, נוכחות וסיכום.
- **חיבור דו-כיווני**: טבלת הרשמות אחת במסד הנתונים משמשת את שני הצדדים. ביטול הרשמה נשמר כהיסטוריה (לא נמחק). נוכחות נשמרת לפי הרשמה ומפגש, ו"לא הגיע" נבדל מ"טרם סומן".
- **אכיפה בצד השרת** בעת הרשמה: חבר קיים, הרשמה כפולה, הגבלות, הרשמה פתוחה, התאמה לקריטריונים ושאלות חובה.
- **דף רישום ציבורי לדוגמה** (`/register/<מזהה סדנה>`), נפתח מכפתור "פתח דף רישום לדוגמה" בכרטיס הסדנה.

## מודול שפ"ח (ליווי טיפול פסיכולוגי חיצוני)

נגיש מתפריט הצד: **ליווי טיפול פסיכולוגי (שפ"ח)**, ומטאב "שירותים סוציאליים" בכרטיס החבר.

- **רשימת תהליכים** (טבלה): חיפוש לפי חבר או מטפל, סינון לפי סטטוס ומסלול, מיון. הכפתור "ניהול מטפלים" פותח ניהול מטפלים בסיסי (שם, סוג פרטי/סמט, מחיר לפגישה, פעיל).
- **פתיחת תהליך** בשלושה שלבים: חבר קיים ופרטים בסיסיים (אישור מיהודה חובה), התאמת מטפל (אפשר לשמור ללא מטפל, ואז "ממתין להתאמת מטפל"), וסיכום. פתיחה מכרטיס החבר משייכת את החבר אוטומטית.
- **כרטיס שפ"ח**, שישה טאבים: פרטים בסיסיים (עם התקדמות "X מתוך Y"), ציר זמן (דיווחים חודשיים לפי חודש מהחדש לישן ואירועים כרונולוגיים), דוחות עו"סית, משובים (תצוגה בלבד), פעולות (החלפת/שיוך מטפל, השהיה, הקפאה, הארכה, סיום, הערות וחריגות) ופרטים נוספים (היסטוריית מטפלים, סטטוסים והארכות).
- **הפעלה לצורך הדגמה**: הכפתור "סמן חוזה כחתום לצורך הדגמה" מעביר לסטטוס פעיל ומתועד כפעולה ידנית. אין חתימה דיגיטלית ולא מוצג מסמך חתום.
- **דיווחים חודשיים**: טיוטה, ממתין לאישור, מאושר. רק דיווח מאושר נספר בפגישות שהתקיימו. התעריף וההשתתפות העצמית נשמרים בדיווח, ולכן שינוי מחיר מטפל לא משנה דיווחים קיימים. אישור הדיווח הוא פעולה חד-פעמית.
- **כללים שנקבעו**: מכסה מאושרת = מכסה בסיסית + הארכות. ביטולים בתשלום מחויבים באותו תעריף ובאותה השתתפות עצמית, ואינם נספרים במכסת הפגישות. לחבר מותר תהליך פתוח אחד בכל רגע, ותהליכים נוספים לאחר שהסתיים הקודם. כשדיווח מאושר ממצה את המכסה, התהליך מסתיים אוטומטית (מתועד כפעולה אוטומטית), וניתן להאריך אותו אחר כך.
- **שילוב בכרטיס החבר**: טאב שירותים סוציאליים (כל תהליכי השפ"ח, כולל שהסתיימו), כרטסת (השתתפות עצמית וסטטוס תשלום) וחריגות (איחור בתשלום, השהיה בעקבות הפרה, חריגה ידנית), בלי לפגוע בחריגות הסדנאות.

### איך בודקים את המודול
1. `npm run db:seed` (בטוח להרצה חוזרת) מוסיף 6 מטפלים ו-8 תהליכי הדגמה מגוונים, ללא מחיקת נתונים קיימים.
2. עברו על תרחיש ההדגמה: פתיחת תהליך חדש לחבר שאין לו תהליך, הפעלה ידנית, שני דיווחים (4 ו-3 פגישות) ואישורם (7 מתוך 30), החלפת מטפל, הארכה ב-10 פגישות, סימון חתימה על חוזה ההארכה (רק אז סה"כ 40), ובדיקת כרטיס החבר.
3. `npm test` מריץ 76 בדיקות: 23 לחברים וסדנאות, 20 לשפ"ח, 14 לפניות וליווי עו"ס, 18 להשלמות לפי מסמך הדרישות, ובדיקה אחת שמריצה את הסידינג על מסד ריק (כמו בפריסה חדשה).

## פניות ובקשות סיוע וליווי עו"ס

שני מודולים נוספים בתפריט הצד: **פניות ובקשות סיוע** ו**ליווי עו"ס**. הרצף: חבר פונה, הפנייה נקלטת, גורם אחראי בודק, מתקבלת החלטה, ונפתח תהליך המשך. הכול מתועד בכרטיס החבר.

- **פניות**: טבלה עם חיפוש (חבר, מספר, נושא), סינון (סטטוס, סוג, אחראי, תאריך) ומיון. כרטיס פנייה בארבעה טאבים: פרטים, טיפול (שיוך, סטטוס, הערה, תיעוד שיחה, החלטה, פתיחת תהליך המשך), היסטוריית פעולות ותהליכים קשורים. סגירה דורשת סיבה. החלטה אינה סוגרת את הפנייה, והפנייה לעולם לא נמחקת.
- **ליווי עו"ס**: מודול נפרד משפ"ח. טבלה וכרטיס בששה טאבים: פרטים, פגישות (מספר הפגישות מחושב), התערבויות ופעולות, דוחות וסיכומים, תהליכים קשורים והיסטוריה. סטטוסים: טרם התחיל, פעיל, בהקפאה, הסתיים, עם פתיחה מחדש ששומרת את כל ההיסטוריה. סיום דורש סיבה וסיכום. כשמספר הפגישות בפועל מצדיק סוג אחר (חד-פעמי עד 2, מתמשך 3 ומעלה) מוצעת הצעה לעדכון, והיא אינה מתבצעת אוטומטית.
- **קשרים אמיתיים במסד הנתונים**: פנייה אל ליווי (מזהה פנייה בתהליך), פנייה אל שפ"ח וליווי אל שפ"ח (טבלאות קישור), וכל אלה מוצגים משני הצדדים. קישור אפשרי רק בין רשומות של אותו חבר, והשרת דוחה קישור בין חברים שונים.
- **שפ"ח**: מתוך פנייה לא נוצר שפ"ח עוקף. הכפתור "פתח תהליך שפ"ח" מוביל למסך הפתיחה הקיים (כולל אישור יהודה), ולאחר היצירה התהליך מקושר לפנייה. אפשר גם לקשר שפ"ח קיים של אותו חבר. שפ"ח עצמו (מטפלים, דיווחים, סטטוסים, תשלומים, הארכות) לא שונה. בכרטיס שפ"ח נוספה רק תצוגת קשרים בטאב "פרטים נוספים".
- **כרטיס חבר**: הטאב "שירותים סוציאליים" מציג שלוש טבלאות (שפ"ח, ליווי עו"ס, פניות), כולל תהליכים שהסתיימו, וכפתור פתיחה לכל אחת. ביטוח לאומי בתהליך נגזר מכרטיס החבר ואינו נשמר כעותק.
- **מניעת כפילות**: מהפנייה כבר נפתח ליווי מוצגת אזהרה עם קישור, ואפשר לפתוח נוסף רק באישור מפורש. לחיצה כפולה על שמירה לא יוצרת רשומה כפולה.
- **נתוני הדגמה**: `npm run db:seed` מוסיף 12 פניות ו-8 תהליכי ליווי (פעיל, הסתיים, בהקפאה, מרובה פגישות, עם התערבויות, מקושר לשפ"ח), בלי מחיקה וללא כפילויות בהרצה חוזרת.

## השלמות לפי מסמך הדרישות

הפירוט המלא, שורה אחר שורה, נמצא ב-[docs/requirements-coverage.md](docs/requirements-coverage.md).

- **סדנאות**: מעברי סטטוס אוטומטיים (מפורסם, מתקיים כעת, הסתיים) שנבדקים בשרת אחת לדקה, וסגירת רישום אוטומטית כשסומן. חובת רישום בשלוש אפשרויות באירועים, סוג מחיר (קבוע/לחודש), שאלות צ'קבוקס, הגבלה "רק מי שלא השתתף בסדנה X" והודעות מותאמות לכל סדנה (דחייה, סיום רישום, אחרי סגירה).
- **דף הרישום הציבורי**: הודעה ייעודית לכל סיבת דחייה, כפי שהמסמך מבקש (לא חבר, כבר רשום, לא מתאים, מוגבל, אי-הגעות חוזרות, רישום סגור), בלי לחשוף גיל, נתוני כרטיס או את הסיבה הפנימית של הגבלה. חסימה אחרי 3 פעילויות חד-פעמיות (או 4 מפגשים של סדנאות מתמשכות) שלא הגיע אליהן בחצי השנה האחרונה חלה על הרשמה דרך האתר בלבד, והצוות יכול לעקוף אותה בהרשמה ידנית.
- **חברים**: הגבלה לפי סוג פעילות, בחירת פעילות להגבלה מתוך אלה שטרם התקיימו בלבד, מיון הפעילות לפי סוג, ספירת חריגות, והערות עו"סית בכרטיס.
- **שפ"ח**: סטטוס "ממתין לחתימת הארכה". **הארכה כבר אינה נספרת מיד**: היא נוצרת וממתינה לחתימת המטופל, ואחרי סימון החתימה (ידני, להדגמה) המכסה גדלה והסטטוס עובר ל"פעיל (הארכה)". סיבות השהיה לפי המסמך, סיבת סיום "טיול לחו"ל", פגישות עם המטופל, משימות לעו"סית, הודעות מטפל, ומספר פגישות לכל מטפל.
- **ליווי עו"ס**: סוג תהליך אוטומטי כברירת מחדל (עד 2 פגישות חד-פעמי, 3 ומעלה מתמשך), מספר סידורי לפגישות, פגישות שבוטלו עם סיבה (לא נספרות), נושאים והתערבויות בפגישה, משך בקטגוריות וקישור פעולה לפגישה באותו תהליך.

### גיבוי ושחזור מסד הנתונים
לפני מיגרציה נוצר גיבוי בתיקייה `server\prisma\backups` (מחוץ ל-Git). לשחזור: עצרו את השרת, והעתיקו את קובץ הגיבוי הרצוי על `server\prisma\crm.db`. המיגרציות מוסיפות טבלאות בלבד ואינן משנות טבלאות קיימות.

### פרטיות ואבטחה (חשוב)
- המודול מיועד לנתונים בדויים בלבד. ה-POC אינו מאושר לשמירת מידע רפואי אמיתי.
- השרת מאזין מקומית בלבד (`127.0.0.1`) כברירת מחדל, ולא נרשם מידע טיפולי בלוגים. בסביבת Render (שמגדירה `RENDER`) הוא מאזין לכל הממשקים, כנדרש לשירות מרוחק.
- אין התחברות והרשאות. אם המערכת פרוסה בכתובת ציבורית, כל מי שיש לו את הקישור רואה את הנתונים, ולכן יש להשתמש בנתוני הדגמה בלבד ולשתף את הקישור בזהירות.

## הערות והגבלות ידועות

- אין התחברות והרשאות, שליחת הודעות, סליקה או אינטגרציות, כפי שהוגדר.
- **הדף הציבורי אינו מאובטח**: זיהוי לפי מספר טלפון בלבד אינו אימות זהות. הדף אינו חושף פרטי חבר ואינו מאפשר ביטול, צפייה או עריכה. מערכת אמיתית תדרוש אימות זהות. עם זאת, ההבחנה בין "לא חבר" ל"חבר" מאפשרת לברר אם מספר מסוים רשום כחבר, וזו חשיפה מוכרת שנובעת מהדרישה להציג הודעה ייעודית ללא-חברים.
- גיל לבדיקות התאמה מחושב לפי שנה נוכחית פחות שנת לידה (לא תאריך יום הולדת).
- ב"סדנה מרובת מפגשים" ללא תאריך התחלה לא נוצרים מפגשים, וניתן להוסיף אותם בטאב "מפגשים".
- שינוי הסטטוס ידני בלבד, ללא מעבר אוטומטי לפי מועדים.
- בהגירה נוסף אינדקס ייחודי חלקי שאינו מיוצג ב-`schema.prisma`. בפיתוח המשך עם `prisma migrate dev`, יש לבדוק שהמיגרציה הבאה אינה מוחקת אותו.
- Windows ו-PowerShell: אם מוצגת שגיאת הרשאות בהרצת `npm`, יש להריץ `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.
